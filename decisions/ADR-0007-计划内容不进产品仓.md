## 背景

产品仓的门禁是**纵切**的：契约、判据、派生面、回执互相绑定，任何一处数字变化都要全量重冻（`verify.sh --full` + 派生面 8 步）。而规划类内容——方案比对、波次复盘、外部决议数据、私有手册——**不参与判据**，却会在两处造成实际损害：

1. **稀释承诺面**：读者无法区分「已经生效并对判据负责的」与「还在讨论的」。历史上多次出现把方案当契约引用的情况。
2. **抬高重冻成本**：计划文档进仓后会被 `doc_hygiene` / `code_metrics` 计入，改一句话就可能触发派生面漂移。

同时，2026-10-20 的工作区迁移（C 盘 → D 盘）暴露了另一个同源问题：**同一产品存在多个本地副本**（旧项目 `NarrativeForge`、gitee 浅克隆、导出快照、若干 worktree），彼此口径不一致，且无法判断哪一个是真身。

## 决策

1. **唯一工作区**：产品只有一个工作真身 `D:\NinFenz`（origin = `github.com:Monyeah777/NinFenz`）。其余副本一律进归档区 `D:\_NF-Archive\`（含全分支 bundle），不再作为工作树。
2. **计划内容进 `D:\NF-Plan`**（独立私有仓 `NinFenz-Plan`）：方案、波次复盘、外部决议数据、私有运行手册、历史审计原件的**新**增内容。
3. **边界判据**：「已经生效、且被判据/代码引用」的进产品仓；「还在讨论、或定完就不再被引用」的进计划仓。
   - 由此推论：`decisions/ADR-*.md` **留在产品仓**（它是 `desktop/src/core/decisions.py` 的数据真源，被 8 个脚本/测试引用），`results/audit` 与 `docs/4x_*` 波次档同样留在产品仓（分别被 6 / 5 个核心模块读取）——它们是判据输入，不是文档。
4. **历史不动**：本 ADR 不追溯搬迁既有内容。把已长进判据的东西挖出来，成本远大于收益，且会制造一批假红。

## 后果

- 产品仓 `git log` 只出现"对判据负责"的变更；计划讨论留在计划仓，可自由迭代而不触发门禁。
- 跨盘迁移暴露的路径假设缺陷（`os.path.relpath` 在 Windows 不同挂载点抛 `ValueError`）已随本 ADR 同期修复：`scripts/nf.py` 的展示面统一走 `_rel_display()`，跨盘退回绝对路径。
- 回滚成本：若将来确需合并两仓，计划仓内容可整体 `git subtree` 并入，但**必须同步更新本 ADR 的 superseded_by**。
